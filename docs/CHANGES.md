## 1. Блокирующие проблемы

Три бага, из-за которых проект не запускался ни на одной машине, кроме авторской. Это была самая срочная категория: работодатель, у которого проект не стартовал, дальше не смотрит.

### 1.1. Захардкоженный путь к `.env`

**Файл:** `apps/internal/config/config.go`

Было:

```go
dir, err := os.Getwd()
dir = "/Users/root1/Desktop/cloudflow/.env.development"   // затирает os.Getwd()
```

Путь к конкретной папке на конкретном macOS. На любом другом компьютере сервер падал при старте. Плюс результат `os.Getwd()` присваивался и тут же затирался — мёртвая строка.

Стало: конфиг читается по приоритету

1. настоящие переменные окружения (работает в Docker, CI, проде);
2. файл `.env` из рабочей директории или родительской (для локальной разработки);
3. значения по умолчанию для необязательных параметров.

Плюс добавлена валидация: если не хватает обязательных переменных, сервер падает с внятным сообщением вместо непонятной ошибки подключения к БД:

```
missing required environment variables: DATABASE_PASSWORD, JWT_SECRET (see .env.example)
```

**Зачем:** конфигурация через переменные окружения — это [12-factor](https://12factor.net/config), стандарт для контейнеризованных приложений. Файл `.env` остаётся как удобство для локальной разработки, но не является обязательным.

### 1.2. Захардкоженный `localhost` в подключении к БД

**Файл:** `apps/internal/database/postgres.go`

Было:

```go
dsn := fmt.Sprintf("postgresql://%s:%s@localhost:%s/%s", ...)
```

Хост зашит намертво. Из контейнера, где база доступна по имени сервиса `postgres`, а не по `localhost`, подключиться невозможно — то есть проект принципиально не мог работать в Docker.

Стало: хост и `sslmode` берутся из конфигурации, пароль экранируется через `url.QueryEscape` (иначе спецсимволы вроде `@` ломают строку подключения), соединение закрывается при неудачном `Ping`, чтобы не текли дескрипторы.

### 1.3. Логгер требовал файл всегда

**Файл:** `apps/internal/logger/logger.go`

Было: `os.OpenFile(env.Server.Lpath, ...)` вызывался безусловно. Если `LOG_PATH` пустой — попытка открыть файл с пустым именем, ошибка, сервер не стартует.

Стало: в режиме `dev` логи идут в stdout и файл не открывается вовсе; в режиме `prod` — JSON в файл, если `LOG_PATH` задан, иначе в stdout (это норма для контейнеров, где логи собирает сам Docker).

## 2. Безопасность и корректность кода

### 2.1. Ошибка проглатывалась при проверке пароля

**Файл:** `apps/security/password.go`

Было — классический err shadowing:

```go
storedHash, err := base64.StdEncoding.DecodeString(parts[5])
salt, err := base64.StdEncoding.DecodeString(parts[4])   // затирает первую ошибку
// ...
computedHash := argon2.IDKey(...)                        // используем данные ДО проверки err
if err != nil { ... }                                    // проверка слишком поздно
```

Ошибка декодирования первой строки терялась, а результат использовался ещё до проверки второй. Стало: каждая ошибка проверяется сразу после операции и оборачивается с контекстом (`verify: decode salt: %w`).

### 2.2. Самодельный парсер чисел

Было:

```go
func fastAtoi(s string) *uint32 {
    var res uint32
    for i := 0; i < len(s); i++ {
        res = res*10 + uint32(s[i]-'0')   // на "abc" молча вернёт мусор
    }
    return &res
}
```

Функция не сообщала об ошибке и не проверяла переполнение: испорченный хеш превращался в произвольные параметры Argon2id, и проверка пароля давала непредсказуемый результат. Заменено на `strconv.ParseUint` с обработкой ошибки.

### 2.3. Формат хеша проверялся слабо

Было: `if len(parts) < 6` — принималось что угодно, лишь бы частей хватало, включая хеши от другого алгоритма. Стало: `len(parts) != 6 && parts[0] != "argon2id"`.

### 2.4. Что в хешировании было сделано хорошо и осталось как есть

Стоит знать, что защищать на собеседовании:

- **Argon2id** — современный стандарт (RFC 9106), memory-hard, устойчив к перебору на GPU. Правильный выбор вместо bcrypt.
- **Соль генерируется через `crypto/rand`** — криптостойкий генератор, а не `math/rand`.
- **Сравнение через `subtle.ConstantTimeCompare`** — защита от timing-атак.
- **Самоописывающийся формат** `argon2id$память$итерации$параллелизм$соль$хеш` — параметры хранятся вместе с хешем, поэтому их можно ужесточить в будущем, не ломая существующие пароли.

Изменено только оформление: конструктор `NewHashPassword` → `NewPasswordHasher`, опции `newMemory` → `WithMemory` (экспортируемые, по общепринятому в Go паттерну функциональных опций), метод `HashFromDB` → `Hash` (старое имя вводило в заблуждение: метод ничего не читает из БД).

### 2.5. Валидация при регистрации

Добавлена проверка минимальной длины пароля (8 символов) — раньше проверялось только имя. Сообщение об ошибке заменено с `"small size name"` на человекочитаемое.

### 2.6. Опечатки в публичном API

| Было | Стало | Где |
|---|---|---|
| `CreatUser` | `CreateUser` | `internal/database/resolver.go` |
| `CreatUser` | `NewUser` | `internal/entity/user.go` |
| `claenup` | `cleanup` | `cmd/server/main.go` |
| `MAX_LENGHT_NAME` | `maxNameLength` | `internal/entity/user.go` |
| `github.com/rrrr22wwww.com/cloudflow` | `github.com/rrrr22wwww/cloudflow` | 16 файлов |

Последнее — опечатка в имени Go-модуля (лишнее `.com`). Мелочь, но она видна в каждом импорте проекта.

### 2.7. Мёртвый код в `main.go`

Удалено ~30 строк закомментированных экспериментов (проверка версии БД, тестовые запросы) и дублирующий entrypoint `apps/server.go` — заготовка от `gqlgen init`, которая не использовалась. Добавлен эндпоинт `/healthz`, проверяющий доступность БД: он нужен для healthcheck в Docker и для мониторинга в проде.

## 4. Тесты

### 4.1. Юнит-тесты: были фиктивными

Было:

```go
func TestVerify(t *testing.T) {
    ok, err := Verify(b64Hash, password)
    if ok {
        fmt.Printf("Verify: simular password - OK\n")
    } else {
        fmt.Printf("Verify: different password - ERR\n")
    }
}
```

Тест печатал результат в консоль, но **никогда не падал** — ни одного `t.Fatal` или `t.Error`. Такой тест всегда зелёный, даже если функция сломана полностью. Плюс переменная `err` объявлялась и не проверялась.

Стало — 4 настоящих теста в `apps/security/password_test.go`:

| Тест | Что проверяет |
|---|---|
| `TestHashAndVerify` | Правильный пароль проходит проверку |
| `TestVerifyRejectsWrongPassword` | Неправильный — не проходит |
| `TestHashesAreSalted` | Два хеша одного пароля различаются (соль действительно случайна) |
| `TestVerifyRejectsMalformedHash` | Битые хеши отклоняются с ошибкой, а не молча |

### 4.2. Интеграционные тесты: новое

**Файлы:** `apps/internal/integration/auth_test.go`, `migrate_test.go`

Поднимают тот же HTTP-стек, что и боевой сервер — Gin-роутер, middleware авторизации, gqlgen-резолверы — и работают против настоящего PostgreSQL. Миграции накатываются автоматически.

| Тест | Что проверяет | Почему это важно |
|---|---|---|
| `TestRegisterReturnsWorkingToken` | Токен из `register` сразу работает для `me` | Сквозной путь регистрации |
| `TestLoginWithCorrectAndWrongPassword` | Верный пароль → токен; неверный и несуществующий email → одинаковая обобщённая ошибка | Отсутствие user enumeration: по разнице ответов нельзя выяснить, зарегистрирован ли email |
| `TestProtectedQueryRequiresToken` | Без токена и с мусорным токеном → 401 | Middleware не пропускает дальше резолверов |
| `TestLogoutRevokesToken` | Тот же JWT после logout → 401 | **Ключевой тест проекта** — доказывает, что сессии поверх JWT работают |
| `TestSessionPersistedInDatabase` | Сессия записана в `user_sessions` | Хранилище не только в памяти |

Тесты изолированы build-тегом `integration` и пропускаются без переменной `TEST_DATABASE_DSN`, поэтому обычный `go test ./...` от них не зависит.

**Что стоит уметь объяснить:** `TestLogoutRevokesToken` — это тест на главное архитектурное решение. Чистый JWT нельзя отозвать: он валиден до истечения срока, что бы ни случилось. Поэтому каждый токен дополнительно проверяется по хранилищу сессий, и logout удаляет запись. Цена — один лишний поиск на запрос, выгода — реальный выход из системы.

## 5. Docker и инфраструктура

### 5.1. `docker-compose.dev.yml` — исправлен

| Было | Стало | Почему |
|---|---|---|
| `image: postgres:latest` | `postgres:16-alpine` | `latest` уже уехал с 16 на 18 сам по себе — источник невоспроизводимых багов |
| `volumes: ./var/lib/postgresql:/var/lib/postgresql` | именованный том `postgres_data` | Данные БД не должны лежать рядом с исходниками |
| `restart: always` | `restart: unless-stopped` | `always` поднимает контейнер даже после ручной остановки |
| нет проверки готовности | `healthcheck` с `pg_isready` | Позволяет другим сервисам дожидаться готовности БД |

### 5.2. Dockerfile — новое

**`apps/Dockerfile`** — многостадийная сборка с двумя целями:

- `server` — статический бинарник (`CGO_ENABLED=0`, `-ldflags="-s -w"`) на минимальном `alpine`, запуск от непривилегированного пользователя, `HEALTHCHECK` на `/healthz`;
- `migrate` — образ с goose и миграциями, запускается как одноразовый контейнер.

Зависимости копируются и скачиваются отдельным слоем **до** копирования исходников — тогда при изменении кода Docker переиспользует закешированный слой с зависимостями и пересборка занимает секунды вместо минут.

**`trade-market/Dockerfile`** — трёхстадийная сборка фронтенда на bun.

### 5.3. `docker-compose.yml` — новое

Полный стек одной командой. Важна цепочка зависимостей:

```
postgres (healthcheck) → migrate (до успешного завершения) → api → frontend
```

`depends_on: condition: service_completed_successfully` для миграций означает, что API стартует только после того, как миграции успешно применились. Без этого API мог подняться раньше схемы и падать на первом же запросе.

## 8. Скрипты запуска

Эта часть родилась из реальных падений при запуске на Windows — каждый пункт исправляет ошибку, которая произошла на практике.

### 8.1. `scripts/common.sh` — безопасное чтение `.env`

Первая версия скриптов загружала конфиг через `source`. На строке

```
SMTP_FROM=CloudFlow <no-reply@example.com>
```

bash упал с `syntax error near unexpected token`, потому что `<` и `>` для него — операторы перенаправления. Коварство в том, что Docker Compose и Go-парсер тот же файл читают нормально: у каждого свой парсер, и файл был валиден для двух потребителей из трёх.

Функция `load_env` разбирает файл построчно и **ничего не исполняет**: снимает кавычки, терпит CRLF от виндовых редакторов, безопасно обрабатывает значения с `$`, обратными кавычками, `|`, `&`, скобками.

### 8.2. `scripts/migrate.sh`

- **Версия goose зафиксирована** (`v3.27.3`) вместо `@latest`. `@latest` означает, что у ревьюера через полгода подтянется другая версия — та же ошибка, что `postgres:latest`.
- **Режим `--psql`** — применение миграций через `psql` внутри работающего контейнера, без единого обращения в сеть. Нужен там, где недоступен Go-прокси (`sum.golang.org`). Каждая миграция идёт одной транзакцией с `ON_ERROR_STOP=1`. Версии пишутся в `goose_db_version` — **ту же таблицу с той же схемой, что создаёт goose**, поэтому после восстановления сети `goose up` увидит применённые миграции и не станет накатывать их повторно.

### 8.3. `scripts/test-integration.sh`

Исправленные реальные проблемы:

| Проблема | Решение |
|---|---|
| `docker compose up -d` возвращает управление до готовности БД → создание тестовой базы падало, а ошибка проглатывалась | Явное ожидание `pg_isready` до 60 секунд |
| `-race` требует cgo и C-компилятора, которого нет в Git for Windows | Наличие gcc определяется автоматически; без него тесты идут без race-детектора |
| Скрипт искал контейнер `cloudflow-postgres`, а существующий назывался `postgres-db` | Переменная `POSTGRES_CONTAINER` плюс автоопределение; существующий контейнер переиспользуется, а не дублируется |
| Спецсимволы в пароле ломали строку подключения | URL-экранирование |
| Повторный запуск падал на существующей тестовой БД | Идемпотентное создание |

### 8.4. `Makefile`

Переписан: логика вынесена в скрипты (в Makefile каждая строка выполняется в отдельном shell, что делает многошаговые сценарии хрупкими). Добавлены цели `env`, `migrate-psql`, `test-integration`, `up`, `down`; наличие gcc для `-race` определяется автоматически.

## 10. Что проверено, а что нет

Честное разделение — важно, чтобы не пообещать на собеседовании больше, чем есть.

**Проверено:**

## Что из этого рассказывать на собеседовании

Сильные стороны проекта, которые стоит уметь защитить:

- **Argon2id вместо bcrypt** — memory-hard, устойчив к перебору на GPU, современный стандарт.
- **Сессии поверх JWT** — компромисс между «токен нельзя отозвать» и «лишний поиск на каждый запрос». Есть тест, доказывающий, что logout работает.
- **Отсутствие user enumeration** — по ответу нельзя понять, зарегистрирован ли email.
- **Чистый SQL без ORM** — осознанное решение ради практики, слой запросов изолирован и заменяем.
- **BFF на фронте** — браузер ходит только в Next API routes, GraphQL-эндпоинт и токены не светятся в клиентском бандле.

Отдельная категория — истории про отладку: кросс-платформенный запуск, `-race` и зависимость от cgo, `source` против `.env` со спецсимволами, недоступный Go-прокси и обходной путь через `psql`. Такие рассказы отличают человека, который свой проект действительно эксплуатировал, от того, кто написал его один раз и забыл.
